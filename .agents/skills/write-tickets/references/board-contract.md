# Default board contract and approval policy

Read before creating `board.json`, revising ticket status, applying approval, or scheduling concurrency. This **default** format is not permission to replace an established project tracker.

## Locations

`<repo>/tickets/board.json` is the editable source of truth. `<repo>/tickets/BOARD.md` is generated by `scripts/ticket_board.py render --write`; edits to the latter are not authoritative and are protected from silent overwrite. Each child `NNN-short-slug/` contains exactly `rd.md` and `eval.md` as authored ticket documents.

## Entry schema

```json
{
  "id": "001-user-login",
  "title": "User login",
  "status": "draft",
  "depends_on": [],
  "resources": ["auth-routes", "session-store"],
  "parallel_safe": false,
  "blocker": null,
  "open_decisions": [],
  "approval": null
}
```

Required fields have exactly the types shown. `depends_on` references an existing ID, never self, and must form an acyclic graph. `resources` names *verified/probable shared edit or external-state areas*, not arbitrary unique per-ticket labels. When impact is uncertain, keep `parallel_safe: false`. Setting `parallel_safe: true` requires at least one explicit non-placeholder resource and a documented ownership/isolation rationale; disjoint strings alone are **not proof** that concurrent writes are safe. `blocker` is null or a descriptive non-empty string. `open_decisions` lists unresolved consequential choices; approved statuses require an empty list.

Allowed statuses: `draft`, `ready`, `in_progress`, `done`. Dependency blockers are derived, not a status. New and materially changed tickets revert to `draft` and `approval: null`. `ready` means the **specific current ticket version** is user-approved; it does *not* mean dependencies are complete.

## Approving an unchanged ticket

1. Show the full current `rd.md`, `eval.md`, dependencies and board metadata to the user for review; record an explicit approval of this version. Vague prior feature requests and automated reviewer opinions are not approval.
2. Confirm no `open_decisions`, no material risks hidden, and structural validation succeeds.
3. Obtain a deterministic fingerprint:

   `python <skill-root>/scripts/ticket_board.py fingerprint --root tickets --id 001-user-login`

4. Set `status` to `ready` and `approval` to `{ "ref": "<specific user approval message or durable review identifier>", "fingerprint": "<64-char output>" }`. The agent must supply genuine evidence; the script checks its presence and staleness but **cannot establish that the user really approved**.
5. Validate, regenerate `BOARD.md`, and validate with `--check-rendered`.

The fingerprint covers the current `rd.md`, `eval.md`, plus the ID/title/dependencies/resources/parallel_safe metadata. Changing any of those, even whitespace in documents, invalidates approval; revert to draft and repeat review. A new blocker can pause launch without changing approved requirements. `in_progress` and `done` require valid approval, but no command in this skill promotes to those states or completes implementation.

## Parallel planning (not authorization)

`BOARD.md` lists eligible `ready` tickets only when their dependencies are `done` and `blocker` is null. The renderer makes conservative candidate batches: a `parallel_safe: false` ticket always stands alone; `parallel_safe: true` candidates may share a batch only when their declared `resources` are disjoint. Batches are alternatives/sequential dispatch groups, **not** authorization to start workers. Before a real parallel run confirm actual overlapping files, worktrees, shared databases/cache/build artifacts, external effects, agent ownership, approvals, and integration/test strategy. Unavailable isolation or unknown shared state means serialize.

## Command contract

All commands use Python standard library only and operate on the explicit `--root` directory. `validate` and `fingerprint` are read-only. `render` prints the proposed Markdown by default; `render --write` changes only the board and refuses to replace an unrecognized or manually modified board. `validate --check-rendered` rejects a stale, absent, or modified board. Any nonzero exit is a failed check, not ready evidence. No command requests or records user authorization; a human must do that.
